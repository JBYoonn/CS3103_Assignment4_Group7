## Notes for the server team: what the client expects

Based on the project requirements (handout) and the 23 Oct meeting decisions. The client depends **only** on the required protocol, so the server can be built any way that meets these points.

| # | Topic | What the client expects from the server | Source | Why it matters on the client side |
|---|---|---|---|---|
| 1 | `HISTORY` first | After every `CLIENT_HELLO`, send `HISTORY` as the **first** message, even if `items` is empty | §4.2 "the server returns a HISTORY message" | The client shows **Syncing…** until `HISTORY` arrives, then **Live** |
| 2 | `HISTORY` contents | Finals only, oldest → newest, leaving out anything at or before `last_segment`/`last_revision`, limited to `history_seconds` | §4.2 | The client merges these without duplicates. Late joiners see them as context; reconnecting clients see them tagged "recovered" |
| 3 | `history_seconds` | Accept up to 60, clamp anything larger, and use a sensible default if it is missing or invalid. The client always sends 60 | §4.2 "up to 60 seconds" | 60 s fills the largest recall tab |
| 4 | Server history window | Keep the last **2 minutes** of finals, dropping entries by timestamp. It must be bounded | Meeting (2-min master queue); §3.8 | Covers a 60 s late join or recovery with spare room |
| 5 | `source_ts` | Forward the source's `source_ts` **unchanged**. Never re-stamp with server time | §4.1 | The client's 15/30/60 s recall window and its new-lecture detection run on the source clock |
| 6 | Revision order | For each segment, never send an older revision after a newer one, and never send anything after its final | §4.1, §4.2 | The client ignores these anyway, but they waste bandwidth and count as noise |
| 7 | Overload policy | When a client lags, drop or coalesce **provisionals only**. Always deliver **every final**, and keep the latest revision of the active segment | §3.11, §4.3; meeting (per-client queue replaces redundant revisions) | The client is tested to accept a final that arrives with no provisionals before it |
| 8 | Catch-up | Go back to sending every revision once the client catches up | §10 Normal Update Coverage | The client shows drafting text again as soon as revisions flow |
| 9 | Slow clients | One bounded queue per client, so a slow client never delays the others. The meeting preferred replacing queued revisions over disconnecting. If the server does disconnect a client, the client reconnects by itself (0.5 s, backing off to 5 s, with jitter) and resumes through `HISTORY` | §3.10; meeting | Reconnecting needs nothing special from the server; it is just another `CLIENT_HELLO` |
| 10 | Lecture restart | On a new `SOURCE_HELLO` (for example `caption_source.py` rerun while recording the demo), clear the per-segment state, history and active segment. Otherwise the new lecture's segments 1, 2, … look like old duplicates | §4.1 (segments start from 1) | No message to clients is needed. The client sees a lower segment number with a newer `source_ts` and resets itself |
| 11 | Active segment on (re)connect | Recommended: after `HISTORY`, send the latest revision of the segment in progress | §6 reconnect/late-join demo | The current line appears straight away instead of with the next revision |
| 12 | `CAPTION_UPDATE` fields | `type`, `session` (`"L1"`), `segment` and `revision` (integers ≥ 1), `source_ts` (a number), `final` (a boolean), `text`. Ignore extra fields from the source. `SOURCE_DONE` doesn't need forwarding | §4.1 | The client rejects invalid updates and drops any other session |
| 13 | No extra messages | The client sends nothing after `CLIENT_HELLO` and ignores unknown message types. Don't make the client depend on any server-only message. `client_id` is a random number per tab, so log it but don't key state on it | Team rule: client and server have no dependencies on each other | Keeps the two sides independently replaceable |
| 14 | Address | `python solution_server.py --port 8765`, binding to `0.0.0.0` | §5 | The client connects to `ws://<page host>:8765` by default (override with `?server=`) |
